# WSD Gateway — универсальный шлюз обнаружения устройств для разных VLAN

**Открытый проект на Go для FreeBSD и Linux**. Автоматически обнаруживает WS-Discovery-устройства на выбранных исходных интерфейсах и публикует их для клиентов в других сетях. Проводник Windows получает локальный XAddr, а шлюз перенаправляет HTTP-запрос метаданных реальному устройству.

**Статус: v0.4.0-alpha.1 — опытная версия.** Не заменяйте работающий v0.3, пока новая версия не пройдёт `scan`, проверку двух устройств и проверку других Windows-клиентов.

## Основная идея

`tcpdump` не используется. Шлюз автоматически отправляет `Probe` с исходного интерфейса в `239.255.255.250:3702`, получает unicast `ProbeMatches`, извлекает UUID, типы, метаданные и реальный IP отправителя. Имя сервера в XAddr **не требуется разрешать через DNS**.

Служба проверяет метаданные HTTP POST (если `verify_metadata: true`), добавляет устройство в ограниченный реестр, отвечает на запросы Windows из другой сети, используя XAddr вида `http://IP_ШЛЮЗА_В_VLAN:15357/UUID/`. При запросе Windows перенаправляет метаданные по адресу реального устройства. Сам SMB остаётся прямым соединением Windows ↔ сервер.

Автообнаружение работает как для Windows-устройств, так и для ряда других WSD-устройств, если те поддерживают XML WS-Discovery 2005/04, имеют корректный UUID, HTTP XAddr и отвечают на WS-Transfer Get. **Полная совместимость со всеми разновидностями WSD не заявлена.**

## Пример конфигурации

`configs/config.example.json` — публичный обезличенный шаблон для GitHub. Поля:

- `sources`: массив сетевых интерфейсов, где находятся реальные WSD-устройства;
- `clients`: интерфейсы, в которых отвечаем Windows;
- `ipv4`: необязательно, если на интерфейсе ровно один IPv4; при нескольких IP обязательно;
- `allowed_cidrs`: необязательно, по умолчанию локальная IPv4-сеть данного интерфейса;
- `http_port`: локальный HTTP-порт на каждом клиентском интерфейсе;
- `admin_socket`: локальный UNIX-сокет управления, права 0600;
- `probe_interval`: интервал автоматического сканирования (`60s`);
- `device_ttl`: срок жизни автоматически найденного устройства (`15m`);
- `max_devices`: предельный размер реестра (по умолчанию 20000);
- `max_responses_per_probe`: максимум UDP-ответов на один запрос Windows (128);
- `discovery_workers`: пул параллельных HTTP-проверок (16);
- `http_concurrency`: лимит одновременных клиентских HTTP-запросов (256);
- `allowed_metadata_ports`: разрешённые порты реальных устройств, по умолчанию только 5357;
- `verify_metadata`: предварительно проверять ответ WS-Transfer Get;
- `static_devices`: необязательный список фиксированных устройств для плавной миграции.

**Ни IP, ни VLAN, ни имена компьютеров не зашиты в исполняемый код.** Источники и клиентские сети задаются через JSON-файл и проверяются при запуске.

## Команды

```sh
wsd-gateway interfaces
wsd-gateway init
wsd-gateway -config /usr/local/etc/wsd-gateway.json check
wsd-gateway -config /usr/local/etc/wsd-gateway.json scan -scan-duration 20s
wsd-gateway -config /usr/local/etc/wsd-gateway.json run
wsd-gateway -config /usr/local/etc/wsd-gateway.json status
wsd-gateway -config /usr/local/etc/wsd-gateway.json rescan
wsd-gateway version
```

`interfaces` показывает интерфейсы с IPv4. `check` проверяет JSON и параметры ОС. `scan` **НЕ включает новую публикацию для Windows, не открывает HTTP-порт**, а только отправляет активные UDP Probes и проверяет метаданные серверов — его можно безопаснее опробовать рядом с существующей v0.3. `status` и `rescan` управляют запущенным процессом через локальный UNIX-сокет.

Команды выполняются непосредственно на FreeBSD/Linux, не в PowerShell. Если управляете сервером из Windows, подключитесь к своему FreeBSD/Linux-шлюзу по SSH, затем выполняйте команды в его оболочке.

## Компиляция, тесты и установка

```sh
go test -race ./...
go vet ./...
make cross
```

В архиве выпуска лежат готовые бинарники для FreeBSD/amd64, FreeBSD/arm64, Linux/amd64, Linux/arm64. Go на сервере не нужен.

FreeBSD: установите бинарник как `/usr/local/sbin/wsd-gateway`; конфиг в `/usr/local/etc/wsd-gateway.json`; скрипт `etc/rc.d/wsd_gateway` — в `/usr/local/etc/rc.d/wsd_gateway`. **Не включайте автозапуск до теста**. Запуск тестовой службы: `service wsd_gateway onestart`. После проверки: `sysrc wsd_gateway_enable=YES`. Логи: `/var/log/wsd_gateway.log`. Для аварийных рестартов применяется `daemon(8) -R 5 -P ...`; PID — супервизора, не дочернего процесса.

Пример миграции для реального NGS поставляется **отдельным приватным файлом**, а не в публичном GitHub-архиве.

## Нагрузочные ограничения и честные пределы

Реестр протестирован на **10 000 синтетических записей**, а потоки HTTP и обнаружения ограничены. Это не значит, что система проверена на 10 000 реальных устройств, 10 000 одновременно активных клиентов или что Проводник сможет их все отобразить: требуются нагрузочные испытания на отдельном стенде. По умолчанию клиенту высылается не более 128 WSD-ответов за Probe. Следующие Probe с другим MessageID ротируют выборку.

При нескольких тысячах устройств рекомендуется выделять зоны/сегменты и проверять мульткаст-нагрузку. Сервер не выполняет L2-мост, а чтение общих папок происходит обычным SMB напрямую.

## Ограничения

Только IPv4 + WS-Discovery 2005/04. Нет трансляции IPv6, полного WS-Discovery 1.1, HTTPS XAddr, подписанных/защищённых WSD-сообщений, динамического Hello/Bye, фильтрации Scopes и трансляции произвольных SOAP-сервисов. WS-Transfer Get должен быть доступен по HTTP. Протокол WSD не аутентифицирует сам источник: внимательно настраивайте `allowed_cidrs`, порты и межсетевой экран.

Нельзя одновременно постоянно держать v0.3 и новый шлюз на том же локальном HTTP-порту и в тех же VLAN: возможны конфликты и дубли ответов. Пройдите `scan`, затем плановое переключение с возможностью мгновенного отката. Netflector менять не обязательно, но возможные повторные объявления надо оценивать по реальным пакетам.
